# ADR-0287：舊審查報告丙組：刪除、重置、記憶清除期間擋住心跳

- 狀態：✅ 已實作（丙-4）。維護者 2026-10-25 核准修正計畫（「照建議：1～5 都選甲」，第 3 題選甲）。
- 日期：2026-10-27
- 決策者：維護者
- 修訂 ADR-0262（決策 9「刪除靈魂前檢查記憶」：整段持有破壞性操作鎖、還有心跳在跑就回 409、清完家目錄後再查一次、取消註冊照實回報）。
- 修訂 ADR-0270（§6「鎖、旗標與並行」：取得順序最前面換成破壞性操作鎖並標記目標；清除旗標也標記目標；刪除靈魂加入互斥）。

## 背景

10/15 的程式審查（Touka #89～#105）丙組第 3 題，在 dev `426dceda` 上核對後仍有效的：

- **刪除不鎖**：`delete_soul` 從記憶、活動紀錄檢查，到清隔離家目錄（會進執行器、可能要好幾秒）、清三個資料夾、取消註冊，整段沒有鎖，也不和重置、記憶清除互斥。
- **心跳不知道**：`/awaken` 只看擁有者名單；刪除前就在跑的心跳迴圈刪完照樣跑完，`finally` 一定寫 `heartbeat_finished`，窗口以分鐘計。重置時也一樣，心跳在重置清完之後照寫。
- **取消註冊吞錯**：五步各自包在 `contextlib.suppress(Exception)` 裡，失敗也回成功。
- 計畫審查第 1 輪另外指出：
  - 心跳另有 `/retrigger` 入口；
  - `/awaken` 回 202 後才由 BackgroundTasks 開跑，這段時間還沒登記、中斷不到；
  - 心跳 `finally` 先清進行中標記，再 `await` 滑動視窗剪裁（要十幾秒）。這段時間刪除會判成「沒有心跳在跑」，剪裁寫舊對話庫時會把 `legacy/{soul}` 重新建出來。

## 決定

1. **破壞性操作鎖**：`agent_reset/orchestrator.destructive_op(target)` 把原本的 `_reset_lock` 包成不等待的版本：
   - 重置、清除或刪除已經在跑就回 409 `AGENT_RESET_IN_PROGRESS`（1415），否則持鎖並標記目標。
   - 檢查、取鎖、標記之間沒有讓出事件迴圈的地方。
   - 重置與刪除都用它。全系統仍是一把：刪除期間別的靈魂的重置、還原也回 409。訊息改成「另一個重置、記憶清除或刪除靈魂正在進行」，畫面與 log 的說法對得上刪除的情況。
2. **標記與心跳登記**：新 `services/destructive_ops.py`。
   - 目標標記可重疊計數：重置和它後面的清除各算一次。
   - 心跳迴圈也在這裡登記自己（同一個對話的兩次各算一次）。
   - 看標記和登記在同一把執行緒鎖裡，因為記憶清除在工作執行緒裡結束。
   - ID 不分大小寫比對，寧可多擋。
   - 只在 Proxy 行程記憶體裡（ADR-0207 單一行程），不寫檔、不需要 `AsyncFileLock`；行程重啟時進行中的破壞性操作也一起結束。
3. **記憶清除標記目標**：`memory_scrub.begin(target)` 標記目標，`ScrubSession.end()` 放行。請求取消後清除在工作執行緒裡繼續跑，標記一直到工作結束，期間心跳照樣擋。
4. **心跳迴圈**（`/awaken` 與 `/retrigger` 共用）：
   - 起點先清上一次殘留的中斷旗標，再登記。登記之後刪除或重置叫它停，不會被起點清掉。以前在健康檢查之後才清，開跑最初幾秒按的停止會被吃掉。
   - 登記時發現已標記就不開跑，什麼都不寫：不寫進行中標記、不寫 `heartbeat_started`。這也擋住 202 之後、還沒開跑的那一段。
   - 每個脈衝前看標記，看到就停（結束原因 `interrupted`）。
   - `finally` 看到標記就不寫 `heartbeat_finished`、不剪裁（禁令 28 的觸發點不變，只是這次略過）。
   - 進行中標記、背景活動與登記移到剪裁之後才清：剪裁期間刪除仍看得到這次心跳在跑。
5. **`/awaken` 與 `/retrigger` 提早回 409**：守衛 B 與能力檢查之後，這個靈魂已標記就回 409 `AGENT_RESET_IN_PROGRESS`。`/awaken` 不寫初始提示；`/retrigger` 不派發，「上次未完成」照留。排程端把 409 當成這次喚醒沒做。
6. **刪除靈魂**：步升、不可刪名單、路徑監獄之後，整段包在 `destructive_op` 裡。
   - 先查這個靈魂有沒有心跳在跑。有就叫它停下，回 409 `SOUL_HEARTBEAT_RUNNING`（1419），什麼都不清。設標記和查心跳之間沒有 await，查完之後才開跑的心跳會看到標記。那次心跳開跑時已寫 `heartbeat_started`，停下後刪除仍會被「還有活動紀錄」擋下，要先重置再刪。
   - 記憶與活動紀錄檢查、清家目錄照舊。清完家目錄後再查一次記憶與活動紀錄：清家目錄要好幾秒，這段期間寫進來的會擋下。
   - 取消註冊五步（模型清單、靈魂登記、主要模型、擁有者名單、身分覆寫）每步都做。有失敗時回 500 `SOUL_UNREGISTER_INCOMPLETE`（1420），`failed_steps` 列出步驟名稱，原始例外只進 log。資料已經刪了，五步都冪等，再刪一次會補清。
7. **重置**：在 `destructive_op` 裡叫這個靈魂正在跑的心跳停下，照常重置、不回 409。停下前寫的東西會照實顯示成「重置後又有新寫入」。
8. **不變的**：
   - 擁有者名單照舊走 `_atomic_users_write`。
   - 沒有新的取鎖順序：破壞性操作鎖只用不等待的方式取，心跳只讀標記。
   - 端點與 OpenAPI 不變，只多兩個錯誤碼。
   - Guard #45 基準、權限與風險分類不變。

## 後果

- 刪除靈魂時心跳正在跑，會先拿到「已經叫它停下，請先重置再刪除」，多一步。
- 刪除期間其他靈魂的重置、記憶清除與系統還原也會暫時拿到 409（那把鎖本來就是全系統一把，這次刪除也加入）。
- 重置或刪除叫停會中斷整個對話：家對話是前景聊天與心跳共用的，正在回覆的前景訊息也會停在下一輪模型呼叫前。
- 已知限制：
  - 仍擋不住這段期間你自己在前景聊天、SNS、群聊對這個靈魂的寫入（第 3 題乙案才擋，要改工具層）。刪除靠清家目錄後的再查擋下，重置會照實顯示「重置後又有新寫入」。
  - 叫停要等正在跑的那一輪模型呼叫回來（`react_core` 每輪呼叫模型前檢查中斷）；重置不等它，停下前寫進來的記憶、對話與剪裁照實留著。
  - 被擋下的心跳不剪裁，下一次心跳或聊天回合結束時才剪。
- 撤回：revert 即恢復原樣；不改任何資料。本 ADR 檔保留，在狀態註記撤回。

## 驗證

- 先寫的測試在修正前 18 個紅（介面先寫成空殼）：
  - 標記計數與不分大小寫、被擋時不能登記、叫停只中斷這個靈魂、同一個對話兩次分開算。
  - 迴圈被擋時什麼都不寫、標記後下一個脈衝前停且不寫結束事件也不剪裁、剪裁時仍登記、開跑最初叫停不被清掉。
  - 刪除：清家目錄期間寫入的事實或活動紀錄會擋下、心跳在跑時叫停並回 409（停下後要先重置才能刪）、重置中刪除回 409、刪除中重置回 409、取消註冊失敗照實回報。
  - `/awaken` 與 `/retrigger` 在標記期間回 409。
  - 重置期間標記目標並叫停這個靈魂的心跳、清除被取消後標記保留到工作結束。
- 「重置失敗後放行」修正前後都綠，是防回歸用。
- 修正後相關測試 185 個全過；Chat `SoulStudio.crud.test.tsx` 44 個全過。
- 變異檢查 25 個全部變紅：
  - 迴圈：開跑不看標記、脈衝前不看、`finally` 不看、清中斷旗標放回健康檢查之後、剪裁前就拿掉登記、結束不拿掉登記。
  - 入口：`/awaken`、`/retrigger` 不擋。
  - 刪除：不查心跳、只查不叫停、不拿鎖、清家目錄後不再查、只再查事實、取消註冊失敗不記、不回報、第一步失敗就停。
  - 鎖與清除：鎖不標記目標、重置不叫停心跳、清除結束不放行、清除不標記目標。
  - 標記本身：分大小寫、被擋也能登記、結束一次拿掉全部、叫停不中斷、放行一次全放。
