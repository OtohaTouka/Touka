## 背景

SNS（Telegram、Discord）進來的請求沒有呼叫者身分，只有機器人綁的靈魂。外人點到別的靈魂有三條路，只有一條有限制：

- **訊息裡寫另一個靈魂的名字、不加 @**：閘道把這則轉給那個靈魂。ADR-0276 §4 規定目標只能是機器人自己的靈魂，或機器人唯一的人類擁有者也擁有的靈魂。這條有限制。
- **Telegram `/switch <名字>`**：任何外人都能打，整台機器人（所有聊天室）換成那個代理人，直到下一次 `/switch`。閘道把換過的當成「機器人綁的靈魂」，ADR-0276 的規則就以它為準，等於外人可以挑任何一位擁有者的任何靈魂。
- **「@名字」**：進群聊（`ToukaGroup`），被點名的靈魂各回一段。群聊會檢查呼叫者能不能驅動每位成員（ADR-0245 修補），但 SNS 沒有身分，這道檢查整個跳過。外人 @ 群聊白名單裡別的擁有者的靈魂，那個靈魂就會回話，它的家原文、前情與舊家尾端也會進回給外人的請求。這件事 2026-11-08 維護者決定先不動、列成候選（ADR-0306、ADR-0307、`SECURITY.md` 殘留風險）；這次一起做。

## 決定

### 1. 拿掉 Telegram `/switch`

刪掉指令處理與「暫時把機器人綁的靈魂換掉、處理完再換回」那段；訊息一律用機器人綁的靈魂交給閘道。之後打 `/switch` 沒有反應（一般訊息的處理本來就排除指令），`/start` 照舊。Discord 沒有指令處理，不用改。

拿掉之後，「整台切過去、之後不用再寫名字」沒有替代：

- 要和同一位擁有者的另一個靈魂接著聊，在訊息裡寫它的名字或別名（不加 @）：存進那個靈魂的 SNS 頻道（家模式是它的家），上下文能延續；但只看這一則的文字，每一則都要寫到那個名字，沒寫、或機器人自己的名字出現得比較多時，就回到機器人自己的靈魂。
- 「@名字」的群聊不存對話，每則都要重新 @，回覆前面標【名字】，被點的靈魂要在群聊白名單裡。

### 2. 共用規則：`utils/sns_reach.sns_may_reach`

`sns_may_reach(來源, 目標, 使用者清單)`（純函式，禁令 18）：

- 來源和目標是同一個靈魂：可以（沒有擁有者也可以）。
- 否則來源要**恰好一位**人類擁有者，而且這位的擁有清單也有目標：可以。
- 其他（來源沒有擁有者、兩位以上擁有者、目標不在那位的清單）：不行。

兩個編號都要先用 `agent_service.identify_agent` 正式化（`ToukaSoulAlice` → `Alice`），這裡逐字比對。停權的使用者照算，和閘道原本的判斷一樣。管理員擁有機器人的靈魂時也不放寬（和 ADR-0276 一致）。

和 `authorization_gateway.shares_human_owner`（ADR-0303）不同：這裡多了「同一個靈魂直接成立」與「來源恰好一位擁有者」（兩位以上擁有者時分不出是誰的機器人，只能叫它自己），不能合併；兩邊註解與 SSOT map 互相連結。

### 3. 閘道

- 「不加 @ 轉給別的靈魂」改用 `sns_may_reach`，規則不變。使用者清單仍只在換目標時才讀：`users.json` 壞掉時，原本就能回的單一靈魂訊息照舊能回。
- 建 pipeline 的 context 時寫入 `sns_soul`：機器人綁的靈魂，正式化過的編號。

### 4. `PipelineContext.sns_soul`

正式欄位（照 `sns_source` 的寫法，說明寫「系統寫入」）。外人改不到它：閘道的 context 是寫死的欄位，外人訊息只進請求的文字；HTTP 聊天端點不把請求欄位抄進 context，而且一定有身分（`require_authenticated`），有身分時這個欄位不被讀；中介層不碰它；群聊成員的 context 是複本。

### 5. 群聊檢查（`dispatchers/group._refusal`）

名單解析之後、查主要模型之前，整個名單一起判斷，有一位叫不到就整輪不派發（連排在前面、叫得到的也不先講）：

- **有呼叫者身分**（網頁、IDE、心跳、計分卡）：照舊用 `can_drive_soul`。`sns_soul` 不被讀，不能放寬，也不影響。
- **沒有身分、有 `sns_soul`**（SNS）：名單裡有不是 `sns_soul` 的成員時才讀使用者清單，每位用 `sns_may_reach` 檢查。讀不到使用者清單也整輪不派發。說明句「群聊只限這個機器人的擁有者的靈魂。」不寫出擁有者是誰。
- **沒有身分也沒有 `sns_soul`**：整輪不派發，回「群聊需要身分，這一輪不派發。」並記一筆 warning。產品程式裡除了 SNS 沒有別的路會沒帶身分進群聊；之後新增的入口忘了帶身分時，在這裡停下而不是放行。
- 沿用前面點名的名單（這一句沒點名）一樣檢查。

SNS 的說明句和「找不到這位靈魂」那句不同，外人可以拿來試某個別名在不在白名單裡。比起修補前能直接和那個靈魂聊天差很多，照留。

### 6. 行為改變

- Telegram 打 `/switch` 沒反應。維護者若在 BotFather 登記過 `/switch`，選單還會顯示，可以自己拿掉。
- SNS 外人「@」別的擁有者的靈魂時，整則不回、只回一句說明。機器人的靈魂沒有擁有者、或有兩位以上擁有者時，只能 @ 它自己。同一句同時 @ 自己的靈魂和別人的靈魂，整句都不回。
- 別的擁有者的靈魂的家原文、前情與舊家尾端不會再進給外人的請求。同一位擁有者的靈魂照舊會帶（維護者 2026-11-07、2026-11-08 的決定）。
- 要更新 Docker 的 ToukaProxy 才生效。

## 不做與已知限制

- 外人不加 @ 寫同一位擁有者的另一個靈魂的名字，機器人就轉給那個靈魂：原本的行為（ADR-0276），照舊。
- 機器人沒有「誰能私訊它」的名單：知道機器人的人都能和它聊（`SECURITY.md` Known Open）。
- `bots.json` 的 `agent_id` 與群聊白名單，管理員或任何擁有靈魂的使用者（用 X-Agent-ID 切成自己的靈魂後）都能改，不檢查擁有者：可以把機器人改綁到別人的靈魂、替任何靈魂加別名。這次擋不住「一般使用者把機器人改綁到別人的靈魂，再從 Telegram 跟它聊」。在「目前只適合互相信任的人使用」的前提下照留，列在路線圖候選。
- 機器人設定的 `is_multi_agent` 閘道沒讀，不加 @ 的名字偵測一律開著；列在路線圖候選。
- 沒有在真的 Telegram、Discord 上驗證；測試用離線建的 Telegram 物件與假模型。

## 測試

`tests/unit/test_sns_reach_security.py`：Telegram 只剩 `/start`；試著 `/switch` 之後訊息仍交給綁的靈魂（在閘道被呼叫的當下記）；純函式的各種情況；真的閘道接真的群聊分發器：別的擁有者的靈魂、整句拒絕、同一位擁有者照常、綁成 `ToukaSoulAlice` 照常、沒有擁有者或兩位擁有者只能叫自己、沿用的名單、讀不到使用者清單、沒有身分也沒有 `sns_soul`、有身分時 `sns_soul` 不影響；閘道只在換目標時讀使用者清單、寫入正式化過的 `sns_soul`。

既有的群聊測試用沒有身分的 context 直接跑分發器，改成帶管理員身分；走 SNS 的帶 `sns_soul`（名單有別的靈魂時另給「同一位擁有者」的使用者資料）。
