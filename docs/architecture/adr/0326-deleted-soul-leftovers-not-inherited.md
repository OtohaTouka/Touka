## 背景

靈魂刪掉之後，依它的編號存放的資料有些沒有刪。管理員再建一個同名的新靈魂，新靈魂就接手舊的東西；新靈魂若指給別人擁有，那個人也一起拿到：

- **心跳排程**：喚醒時只看「現在誰擁有這個編號」，舊排程照原本寫的開場提示、權限（可能是 YOLO）、指定模型跑起來。
- **身分設定**（`identity_map.json` 的 `agent_overrides`）：舊版留下、或刪除時沒寫成的角色設定，套在新靈魂上。刪除時寫不進去目前也不會被發現（回傳值沒看）。
- **統計**（`data/stats/<編號>`）：token 用量、今天的自主次數、當機未完成的標記。開了花費上限時，新靈魂可能一出生就被擋。
- 另外，用編輯建立靈魂（只有重新輸入密碼的管理員能用）少了「建立靈魂」有的兩道檢查：和自訂模型同名（共用擁有清單、看板、統計與記憶）、和人類帳號同名（靈魂會被當成那個人）。

SNS 機器人的綁定、舊對話、對話封存與個人空間也會被接手：機器人在 PR 2 處理（決定 9），其他在 PR 3（決定 8）。

## 決定

### 1. 名字的兩種寫法

`utils/agent_spellings.legacy_spellings(編號)` 固定回兩個值：編號逐字、`ToukaSoul`+編號；DebugAgent 沒有前綴寫法，回兩次自己（對話資料庫的 SQL 寫死 `IN (?, ?)`，禁令 24）。對話列的 `_session_agent_candidates` 改用它。只比對逐字：只差大小寫的是另一個代理人（ADR-0303、ADR-0325）。

### 2. 刪除靈魂

- **鎖內**（破壞性操作鎖，ADR-0287）：刪看板之後、刪儲存之前刪統計（`agent_leftovers.remove_stats_on_soul_delete`，經 `resource_manager.remove_dir`）。刪不掉不擋（任何例外都接：這時看板已經刪了，不能讓意料外的例外把刪除變成 500、留下一半），回應的 `skipped` 多一個 `stats`。
- **身分設定**：取消註冊的 `identity_override` 那步改成 `permission_service.remove_agent_overrides(兩種寫法)`，讀不出來或寫不進去就算失敗，整個刪除回 `SOUL_UNREGISTER_INCOMPLETE`（`failed_steps` 含 `identity_override`），再刪一次會補清。
- **鎖外**：放開鎖之後、回應之前 `clean_up_after_delete`（PR 2 起；PR 1 時叫 `remove_schedules_after_delete`）：先停用綁著它的機器人（決定 9），再刪排程，最後等機器人停下來。會連網路的事不在鎖內做。刪排程前先確認名字仍然不屬於任何代理人（`mission_boards.is_unclaimed`）。放開鎖到這個判斷之間沒有 await（PR 2 加的停用是同步的），同名的新靈魂不可能在這時建好，所以「有人用」只會是這次刪除沒做完（資料夾沒刪掉、登記表沒寫成，`_update_agents_registry` 會吞掉寫入例外、回應照樣 200，或 `custom/<名字>` 留著）：這時排程不刪、記警告。整段最多 15 秒（`SCHEDULE_CLEANUP_SECONDS`）。名字有人用、連不上、逾時、結果不明或其他例外都記警告，刪除照樣成功，`skipped` 多一個 `schedules`（PR 1 時只記警告、回應不變）；舊排程這時沒有擁有者，喚醒時會被拒絕，建立同名靈魂時會再清一次。
- 回 `SOUL_UNREGISTER_INCOMPLETE` 時，`skipped` 的內容也寫進 log。

### 3. 建立靈魂

所有會拒絕的檢查都通過之後、第一個寫入之前（和 ADR-0325 清看板同一個位置），先判斷一次名字屬不屬於任何代理人（`mission_boards.new_board_unclaimed`），結果同時給 `agent_leftovers.clear_for_new_soul` 與 `prepare_new_board`（多一個可選參數 `unclaimed`，不傳時照舊自己判斷，自訂模型不用改）。

不屬於任何代理人時，`clear_for_new_soul` 依序：

1. **排程**：用系統清理的排程橋刪兩種寫法的排程。排程放第一個：它是唯一會因為連不上而拒絕的一步，拒絕時機器人、看板、身分設定、統計都還沒動。心跳位址設定了卻連不上、結果不明、位址寫錯，就回排程橋的錯誤碼（例如 502 `HEARTBEAT_UPSTREAM_FAILED`），什麼都不建。沒設定心跳位址時不檢查、記警告。
2. **機器人**（PR 2，決定 9）：停用綁著這個名字的；`bots.json` 讀不出來或寫不進去回 `SYSTEM_ERROR`，不建立（正在跑的照樣先停）。
3. **身分設定**：刪兩種寫法的覆寫；讀不出來或寫不進去回 `SYSTEM_ERROR`，不建立。
4. **統計**：刪 `data/stats/<編號>`；刪不掉回 `SYSTEM_ERROR`，不建立。

屬於某個代理人時一律不清（那是它的）。

### 4. 用編輯建立靈魂

- **新資料夾或轉換既有資料夾**：在別名與向量 collection 檢查之後，加上和「建立靈魂」一樣的兩道檢查：人類帳號同名回 422 `VALIDATION_ERROR`、自訂模型同名（有 `config.json` 的）回 409 `MODEL_ALREADY_EXISTS`，什麼都不建、不改。檢查抽成 `_refuse_human_id`、`_refuse_custom_model_id`，「建立靈魂」照原本的先後與錯誤碼呼叫同一組。
- **新資料夾**：除了看板用的判斷，名字還在某人的擁有清單，或模型清單（`models.json`）有這個名字或 `ToukaSoul`+名字（停用、離線的也算；`get_model_ids` 只回開啟且在線的，不能用），算「修復資料夾不見的既有靈魂」：什麼都不清（看板也不清，這是 ADR-0325 的行為改變），也不改擁有者。都沒有才清（同決定 3）。
- **轉換既有資料夾**：不清（是它自己的）。

### 5. 身分設定的寫入鎖

- `permission_service.edit_identity_map(mutate)`：模組層級的 `threading.Lock`（和 `users.json` 的 `_users_file_lock` 同一種；Proxy 只跑單一程序，禁令 37 禁的是 `FileLock`），鎖內從磁碟重讀原始 JSON（不經記憶體快取），交給 `mutate` 改，原子寫回，立刻 `_load_identity_map()`（不等 2 秒一次的熱重載）。`mutate` 回 None 是拒絕、回同一個物件是沒有改動（都不寫）。
- `remove_agent_overrides(編號們)`：只刪 `agent_overrides` 裡這些鍵，其他欄位原樣保留；檔案讀不出來回 False、不寫。
- `/identity` 存檔整段改用它：檔內畫面上看不到的舊覆寫（不能有代理角色的編號）在鎖內從磁碟讀，不讀快取，剛被刪除靈魂清掉的不會寫回；格式不對的略過並記警告。檔案讀不出來時照寫管理員送來的內容（能從畫面修好壞掉的檔）。
- `update_identity` 沒有呼叫端了，刪掉（禁令 46）。

### 6. 排程橋的系統清理

- `HeartbeatScheduleBridge.delete_for_agent(兩種寫法)`：讀一次全部排程 → 帶這次讀到的版本號刪第一筆符合的 → 再讀。版本衝突（`HEARTBEAT_REVISION_CONFLICT`）與找不到（`HEARTBEAT_SCHEDULE_NOT_FOUND`）就重讀；其他錯誤碼原樣往外丟。總次數上限是一開始符合的筆數加 `DELETE_RETRY_ALLOWANCE`（5），用完還有符合的丟 `HEARTBEAT_OUTCOME_UNKNOWN`（刪除回成功、排程卻還在時不會一直轉）。只碰 `can_manage` 放行的編號。
- 系統清理用的橋由 `agent_leftovers._system_bridge()` 建，`can_manage` 一律放行，只給這個模組用；位址、`follow_redirects=False`、10 秒逾時與單送照 ADR-0230。
- 排程的並發由心跳服務的版本號處理（ADR-0230），Proxy 不另外加鎖。

### 7. 自訂模型不處理統計

跟自訂模型聊天時，動作的身分是人類（MonitorLayer 只在目標是靈魂時換身分），token 用量與自主紀錄記在人類名下，自訂模型自己沒有統計。若在刪除自訂模型時刪 `data/stats/<模型名>`，模型名和某個人類帳號同名時反而會刪到那個人的統計。所以自訂模型的刪除與改名不處理統計；測試鎖住「聊自訂模型時身分仍是人類」這個前提。

### 8. 之後的 PR（各自開工前寫細節、另審）

- **PR 2：SNS 機器人**：已實作，見決定 9。
- **PR 3：舊對話、封存、個人空間**：刪掉的靈魂的對話只留給當時聊天的人與管理員；靈魂自己的心跳、SNS 頻道不給新靈魂接著用；刪除時沒刪成的封存與個人空間，建立時不讓新靈魂拿到。

### 9. PR 2：SNS 機器人（2026-11-21）

修補前：刪除靈魂不碰 `bots.json`，也不碰正在跑的機器人。刪掉之後閘道認不出它、拒絕外人的訊息；同名新靈魂一建好，綁著舊靈魂的 Discord／Telegram 機器人就接到新靈魂。升級前留下的（刪掉的靈魂的機器人還開著）在 Proxy 啟動時照樣啟動。

- **停用**（`bot_service.disable_bots_for(identity) -> BotsDisabled`，同步、不丟例外）：
  - 鎖內讀 `bots.json`（嚴格：檔案不存在當成沒有機器人；讀不出來、不是 dict、平台的值不是 list 都算失敗），用純函式 `disable_bound(config, 兩種寫法)` 把綁著這個名字（逐字、`ToukaSoul` 前綴、舊格式 dict 攤平後）、而且開著的條目設 `enabled: false`；token、`id`、`agent_id` 與其他條目都不動；有關掉才寫回。任何失敗記下來，`config_ok` 為 False。
  - 不論設定寫不寫得成，執行清單裡綁著這個名字的 adapter 一律設 `retired = True`、移出清單（沒有 await），交給 `stop_adapters` 平行停，每個最多 `BOT_STOP_SECONDS`（10 秒），停不下來只記警告（log 只寫綁的名字，不寫執行清單的鍵，鍵裡有 token 開頭）。其他機器人不停、不重啟。
- **刪除靈魂**：放開鎖之後一律停用，不看名字有沒有人用（放開鎖到這裡沒有 await，綁著這個名字的機器人這時接不到任何靈魂；看判斷反而會在刪除沒做完時漏停）。設定沒寫成列進 `skipped` 的 `bots`。等機器人停下來放在清排程之後，包在 `finally` 裡（請求被取消也照停）。
- **建立靈魂**：名字不屬於任何代理人時，排程之後停用（決定 3）；設定沒寫成回 `SYSTEM_ERROR`。用編輯建立判定為修復時不動。
- **停用的機器人**：`BaseSNSAdapter.retired` 是類別屬性（預設 False）。閘道 `on_event` 最前面看到 `retired` 就丟 `SESSION_SCOPE_MISMATCH`（adapter 照舊回外人「內部錯誤」），停不下來時安全也不靠停下來；Telegram、Discord 的 `start()` 看到 `retired` 不啟動，Telegram 啟動途中被停用的在 `start_polling` 之後自己停（停用那次的 `stop()` 還停不到）。
- **整批重載**（`stop_bots`，存設定頁與關機）：先換成新的空清單、舊 adapter 全標 `retired`，再交給 `stop_adapters`。不再一邊迭代字典一邊 await（停用可能在這時改同一個字典）。`send_external_message` 迭代快照。
- **鎖**：`bot_service.locked()` 回模組層級的 `threading.Lock`。設定頁的讀取遷移（補 `id`）、存檔（讀、合併 token、寫）與停用的讀改寫都在鎖內；三條的讀與寫都是同步程式，鎖內沒有 await、沒有網路，重載在鎖外。和決定 5 一樣用程序內鎖（`bots.json` 只有 Proxy 寫，Proxy 只跑單一程序）。
- `flatten_agent_id` 從 `routers/bots.py` 搬到 `bot_service`，路由與停用共用。
- 不發 ConfigChange hook：刪除、建立靈魂順帶改 `models.json`、身分設定時也不發。
- 只處理靈魂：閘道要求機器人綁的是靈魂，綁自訂模型的機器人本來就不能用，刪自訂模型不用停機器人。

## 沒選的做法

- 排程放在刪除的鎖內刪：會連網路（最多 10 秒逾時）的事放在破壞性操作鎖裡，別的重置、刪除要跟著等。
- 心跳服務連不上時刪除也擋：維護者要能刪掉靈魂；舊排程這時沒有擁有者，喚醒時會被拒絕，建立同名靈魂時會再清。
- 建立時連不上就跳過排程檢查：新靈魂會接手舊排程，正是這次要擋的。
- 另開一個設定項給排程橋：維護者要在 `.env` 多填一項（PR 0 改成接受 `/trigger` 位址）。
- 身分設定用鎖檔（`AsyncFileLock`）：取消註冊與 `/identity` 存檔是同步程式；Proxy 只跑單一程序，程序內鎖就夠。
- 自訂模型刪除時也刪統計：見決定 7。
- 不分大小寫比對名字：只差大小寫的是另一個代理人。
- PR 2：`bots.json` 用鎖檔（`AsyncFileLock`）：三條讀改寫都是同步程式，只有 Proxy 一個程序寫，程序內鎖就夠（同決定 5）。
- PR 2：在破壞性操作鎖內停用：停 adapter 要連平台，Telegram 的 `Application.stop()` 還會等正在處理的那則（`update_queue.join()`），別的重置、刪除要跟著等。
- PR 2：停用後整批重載：其他機器人會斷線重連，正在回的訊息被打斷。
- PR 2：刪掉 token 或清掉 `agent_id`：token 是維護者填的，刪了要重填；`agent_id` 留著，`bots.json` 看得出原本綁誰。
- PR 2：刪除時看「名字有沒有人用」再停用：放開鎖之後沒有 await，有人用只會是刪除沒做完，看判斷反而漏停。

## 已知限制

- 名字還留在登記表（例如刪除時取消註冊沒做完、權限設定的代理人對應在啟動時補進登記表），或 `custom/<名字>` 留著沒有設定檔的資料夾時，算「有人用」，建立時什麼都不清。和看板同一套規則。
- 本機沒設定心跳位址時，排程頁本來就不能用，建立靈魂也不會清舊排程；心跳服務若自己在跑，舊排程照舊會跑。Docker 一定有設定。
- 心跳位址寫成排程橋不接受的形式（例如舊的 `ToukaProxy/.env.example` 註解範例 `/v1/heartbeat/awaken`）時，建立靈魂會回 502、建不起來，要把位址改成心跳服務的根或 `/trigger`。
- 刪除時沒清成的項目列在回應的 `skipped`（`stats`、`bots`、`schedules`；PR 1 時排程只記 log），網頁不會顯示（刪除結果目前只顯示成功），伺服器 log 有警告；建立時會再清一次。
- PR 2，過期的設定頁表單：設定頁開著沒重新整理，在別的分頁刪了靈魂再按存檔，會整份覆寫、把舊的「開啟」寫回去（鎖擋不住過期的表單）。在建立同名靈魂之前存的，建立時會再停用；在建立之後才存的，機器人重新打開、接到新靈魂。能存設定頁的是管理員與任何擁有靈魂的使用者（ADR-0327），他們本來就能把機器人綁到任何靈魂。「存檔帶版本號、拒絕過期表單」列路線圖候選。
- PR 2，建立靈魂前就把機器人設給那個名字（設定頁只有在一個代理人都沒有時才能手打名字）：建立時會被停用，要再打開一次。被停用的機器人：名字還沒重建時，設定頁的選單顯示空白（選單裡沒有這個名字）；重建同名靈魂後，選單會顯示這個名字、開關關著，打開前先確認要把這個機器人給新靈魂（綁 `ToukaSoul` 前綴寫法的，重建後仍然空白）。
- PR 2，升級前的殘留、名字還在登記表：建立時算「有人用」、不清，這種機器人不會在建立時停用。升級後的刪除一律停用，不會再產生這種殘留。
