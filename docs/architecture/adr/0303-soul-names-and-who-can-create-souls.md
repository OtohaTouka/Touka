# ADR-0303：靈魂名稱與建立權限

- 狀態：✅ 已實作。一頁計畫由維護者核准，實作計畫經兩輪審查；實作經四位審查（含兩位對抗式）後修正。
- 日期：2026-11-07
- 決策者：維護者
- 相關：ADR-0142（靈魂的編輯與刪除要重新輸入密碼）、ADR-0147（靈魂與使用者 ID 不能撞名）、ADR-0239（授權閘道）、ADR-0277（建立或重新註冊靈魂時的對話標記）、ADR-0293（代理人資料夾不跟隨連結）。
- 影響範圍：`ToukaProxy/src/routers/souls.py`、`src/routers/custom_models.py`、`src/routers/stats.py`、`src/routers/debug.py`、`src/routers/ui_sessions.py`、`src/services/soul_service.py`、`src/services/resource_manager.py`、`src/services/agent_service.py`、`src/services/authorization_gateway.py`、`src/services/avatar_service.py`、`src/utils/soul_io.py`；`ToukaMemory/src/memory_server/services/manager.py`、`tools/core_file_ops.py`、`utils/drive_bound.py`。

## 背景

靈魂、代理人與使用者的名稱會拼成資料夾路徑，例如 `<data>/soul/<名稱>`。以前有兩個問題：

- **名稱沒有檢查就拼進去**。在 Windows 上，網路分享寫法的名稱拼上去會變成網路路徑；檢查之前的 `exists()`、`resolve()` 就會先連出去。
- **不分大小寫的檔案系統**（Windows、macOS）上，只差大小寫、Windows 的 8.3 短檔名、Unicode 正規化不同的名稱，都會指到同一個資料夾。可是系統其他地方（擁有清單、不可刪名單）是逐字比對，結果別名會被當成另一個沒人擁有的代理人。

另外，「編輯靈魂」能建立新靈魂，或把還沒標成靈魂的舊資料夾轉成靈魂；除錯身分，以及一般使用者切成自己的靈魂之後，也都能這樣做。

## 決定

1. **名稱必須是單一段**（`is_zone_segment`），檢查之後才碰檔案系統。下列地方不合規時都不拼路徑：
   - 靈魂的查詢（`soul_service`）；
   - `get_vault_path`（回 None，只記 debug：一般模型的 ID 像 `ollama/llama3:8b`，每個請求都會走到）、`get_stats_path`（422）；
   - 頭像；
   - 靈魂三個端點；
   - 舊對話統計與同步；
   - ToukaMemory 的 legacy、soul 資料夾。ToukaMemory 在 proxy 不給路徑時，不再用原本的名稱自己拼路徑；把一般模型的對話切分存進舊對話庫時回 422。
2. **已經有的資料夾，名稱要逐字出現在目錄列表裡**。不在列表、檔案系統卻說它存在，就是別名。判斷存在交給檔案系統，所以大小寫、短檔名、正規化都擋得到。Linux 上真的並存、只差大小寫的兩個名稱，各自逐字在列表裡，照常可用。
   - **查靈魂**時別名不算靈魂；`soul/` 底下的檔案也不算。
   - **新的代理人 ID**（建立靈魂、用編輯建立或轉換靈魂、建立或改名自訂模型）不能是任何代理人資料夾的別名：`soul`、`legacy`、`custom`、`stats` 與個人空間都查（`check_new_agent_name`），否則 422。只改大小寫的自訂模型自我改名不擋，那指的就是自己的資料夾。
   - **編輯既有靈魂**只寫 `soul/<id>`，只查這一個位置（`check_soul_folder_name`）。
   - **刪除**會清 `soul`、`legacy` 與個人空間，三個都要查（`check_soul_name`）；不可刪名單（DebugAgent）不分大小寫比對。
   - 列表列不完整、或個人空間的根解析不到時不動（500）。
3. **擁有權**（`is_owner` 的非人類那條路）：
   - Owner 角色跨擁有者的判斷：逐字找不到擁有者時，再用只差大小寫的寫法找；找到的擁有者和自己不同就拒絕。這只用來拒絕，不會讓權限變寬。
   - 逐字找不到擁有者時，Owner 角色只能碰逐字已知的代理人：系統代理人、靈魂、有設定的自訂模型、註冊表的 ID。
   - 30 天寬限期只看逐字的擁有者，和以前一樣；System 角色與自己存取的放行不變。人類那條路照舊逐字比對。
4. **誰能用「編輯」建立或轉換靈魂**：
   - 只有重新輸入密碼的人類管理員。管理員用編輯建立或轉換時，也照建立時一樣檢查名稱與向量 collection 撞名。
   - 非人類只能編輯逐字存在、而且已標成靈魂的資料夾。被拒時在驗證模型之前就回 403：
     - 除錯身分可以編輯任何這樣的靈魂；
     - Owner 角色（一般使用者切成自己的靈魂）只能編輯自己，或和自己有同一位人類擁有者的靈魂（`shares_human_owner`）。沒有擁有者的靈魂不行。
5. **路徑比對**（`same_drive`）：
   - 檔案工具解析目標之前，以及登記專案根目錄時解析之前，都先用字面比對磁碟或網路分享的開頭，和根（工作區）不同就不收。根是相對路徑、對應的磁碟機或跨磁碟的連結時，字面和解析後的磁碟不同，兩個都算。
   - Windows 會原樣交給系統的內部路徑寫法一律不收，看不出它指到哪個磁碟或分享。
   - 專案根目錄在 Windows 上必須是有磁碟也有根的絕對路徑。Linux 不要求：Docker 裡的專案根是主機的 Windows 路徑，和工作區根對著同一個目前資料夾解析，照常可用。
   - 專案本來就必須在工作區裡，所以正常的專案不受影響。

## 取捨與影響

- **升級後的改變**：
  - 名稱不合規的既有靈魂（例如 Windows 上結尾是點）不再被認得。
  - 資料夾大小寫和登記的 ID 不一致的靈魂不再被認得，日誌會有一條警告，要手動改成一致。Windows 上手打 ID 的地方（SNS bot 的代理人、心跳排程、群組白名單、身分對應、外部用戶端的模型名、權限設定的代理人對應）大小寫要和 ID 一致。
  - `legacy`、個人空間的資料夾大小寫和靈魂 ID 不同時，照常能用、能編輯，但不能刪除，要先把資料夾改成和 ID 一致；日誌會寫是哪個位置。
- **除錯身分不能再用編輯建立或轉換靈魂**。`config.json` 損毀或讀不到時，那個資料夾不算已標成靈魂，所以只剩管理員能用編輯修。
- **回應碼的改變**：
  - 舊對話的統計與同步端點，對不在代理人清單裡的 ID 回 403。這也包括已刪除代理人留下的 legacy 資料夾。
  - 自訂模型的端點：Owner 角色查不存在的模型，從 404 變成 403。
  - 把一般模型（ID 不能當資料夾名）的對話切分存進舊對話庫：從 500 變成 422。
- **「已知的代理人」有兩種範圍**：內容快照與舊對話端點用代理人清單（含群組這類設定項目）；`is_owner` 沒有擁有者時用逐字已知的 ID（不含群組）。所以 Owner 角色對群組這類項目從放行變成拒絕，都是收緊。
- **成本與快取**：
  - 查靈魂時，資料夾存在才列一次 `soul/`。上一次列出的名稱以根目錄的修改時間為鍵記住，最多沿用 2 秒；只拿來確認「名稱在列表裡」，不在裡面一律重列，所以不會漏掉剛建立的靈魂。重啟就清空。
  - 修改時間精度粗或不更新的檔案系統（FAT、部分網路或容器掛載）上，只改大小寫的改名之後，舊名稱最多還會被認得 2 秒。
  - 有一項讀不到時用列得到的部分判斷，日誌記「列不完整」；建立、編輯、刪除的名稱檢查要列完整才動。
  - 用別名查詢時每次都會重列（只記住正向的結果，避免剛建立的靈魂被舊結果擋掉）。
  - `is_owner` 在沒有擁有者時依序查已知 ID，查到就停。
  - 實測數字記在 PR 說明。
- **已知的限制**：
  - 同一個磁碟上指向網路分享的符號連結，檔案工具解析時仍會跟過去。建立這種連結在 Windows 需要額外權限，有終端機的代理人本來就能直接連網路。
  - 刪除靈魂時不檢查隔離暫存區的家目錄是否為別名（要重新輸入密碼的管理員才能刪）。
- **不在這次範圍**：自訂模型既有 ID 的別名（`custom/` 的編輯與覆寫）、模型自填專案編號、`/mission` 看板。

## 驗證

`tests/unit/test_soul_name_path_security.py`、`tests/unit/test_drive_bound.py`。兩道測試防線：任何碰到哨兵網路主機的檔案系統呼叫都判失敗，寫到沙盒外的動作直接失敗。

- 在不分大小寫的 Windows 本機用實際的大小寫別名與 8.3 短檔名測。
- Linux CI 用「存在但不在列表裡」的模擬測別名、快取與 Docker 的主機路徑。
- 每一道新檢查都做過改壞驗證：拿掉之後對應的測試會轉紅。
