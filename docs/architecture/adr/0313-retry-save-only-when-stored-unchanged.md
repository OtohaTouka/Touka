# ADR-0313：「僅重試保存」只在存檔沒有別人的新內容時可用

## 背景

對話存檔失敗後，畫面有「重新核對保存結果」和「僅重試保存」。重新核對時畫面已經讀到伺服器的最新存檔，但「僅重試保存」把這一頁的整份草稿配上**伺服器最新的版本號**送出。後端只比版本號，對得上就整份寫入，於是心跳（或別的裝置、工具）剛寫進同一段對話的內容被蓋掉。2026-11-06 實際驗證確認過：按之前存檔裡有心跳的提問與回覆，按之後只剩這一頁送的那一則。現有測試把「重試後遠端變成草稿」當成正確結果。

後端的版本號機制本身沒有問題，問題在畫面拿新版本號替舊草稿背書。

## 決定

1. **重試前先比對。** 每次存檔失敗，畫面記下「這次送出根據的底」。重新核對讀到的存檔和這個底對得上，才代表這段時間沒有人寫過，才給「僅重試保存」；對不上就不給，重試也不送出。
   - 一般存檔失敗，或回覆沒寫進後端（沒有文字、模型失敗、被 hook 擋下、沒送出存檔）：底是這一頁最後確認過的版本，比內容。存檔前要先讀一次存檔、而那次讀取失敗時也一樣：只是沒讀到，底照樣是最後確認的內容。
   - 回覆收尾存檔失敗、後端已先存好回覆的文字版：畫面拿不到文字版的內容，只有版本號，比版本號。後端重啟過版本號會變，只能改用存檔內容，這是安全的方向。
   - 比的是重試會送出的欄位（草稿的 `sessionWritePayload`），每個都要求底有、而且和存檔相同；家的兩欄不算（ADR-0301）。只有存檔有的欄位不會被送出，後端只改有送出的欄位（`model_fields_set`），所以不會被蓋掉；唯一的例外是模式：存檔的人沒有權限維持 Auto／YOLO 時，後端會把模式降回 Manual（`_authorized_changes`），這是既有的權限規則，這個身分的任何一次存檔都一樣，不是重試新開的路；這一頁新建、欄位不齊的對話也因此能重試。比內容而不是版本號，後端重啟後內容沒變也能重試。
   - 底裡缺了要比的欄位、底沒對上就被擋下（bindBase）、接過剪裁：判斷不了，不留底，不准重試。
   - 剪裁接得上（ADR-0302）照舊可以重試。重試再失敗時，下一次的底是重新核對讀到的那份存檔；那次重試若是接剪裁送出的，不留底，免得之後整棵寫回、撤銷剪裁。
   - 能不能重試在重新核對時算一次；草稿一變，核對結果就清掉，要重新核對。
2. **存檔有別人的新內容時，改給「改用存檔內容」。** 先跳確認；按下去重讀一次存檔（不用重新核對時留下的舊快照）並換上，捨棄這一頁沒存進去的修改，重算則數，接著重新載入這段對話、清掉「有新內容」提示；重新載入時重抓到的模式和畫面不同，畫面模式跟著存檔。確認提示不會自己消失，換了對話之後才按確認不生效。換不成（讀不到、存檔被刪、這段時間又有新修改）時跳出存檔失敗的提示。送出時存不進去的那則訊息本來就留在輸入框（只有真正開始回覆才清），看過心跳的內容後可以直接再送。存檔已被刪掉時回報找不到，不換內容。
3. **匯入照確認視窗的承諾覆蓋。** 匯入前的確認視窗寫著「會覆蓋現有的同 ID 對話且無法復原」，原本實際上會被擋下，只能靠重試硬蓋過去。改成：使用者同意後，匯入的那次存檔直接覆蓋，限制如下。
   - 只有確認視窗算進「會覆蓋」的編號（畫面清單上已有的）。視窗算成新的、伺服器其實已經有的（例如心跳剛建、畫面還沒抓到的對話），照舊要求存檔裡沒有。
   - 同意只對那一次存檔有效，由 `syncSession` 的參數帶入，不記在畫面上；之後的一般存檔不帶這個權限。
   - 覆蓋前先讀一次存檔，以它為底、帶它的版本送出；讀完到送出之間有人寫，後端照樣擋下。那次存檔沒確認時照第 1 點比這個底：存檔還是同意當時讀到的那份（例如只是回應遺失），重試等於把同意的覆蓋做完；有人寫過就不准。
   - 那段對話在畫面上本來就停在存檔失敗時，匯入內容會先顯示出來、但不送出；之後重新核對，存檔沒人動過時重試會把匯入內容寫上去，仍在同意的範圍內。
   - 這是對 ADR-0231 第 8 點的刻意例外：原本規定外部整棵樹不算保存證據，不能拿伺服器的新版本替它背書。這裡的背書來自使用者在確認視窗的同意，範圍只到那一次存檔。
4. 後端與 API 不變。

## 修訂

- ADR-0231 第 10 點：「取得有效 revision 且明確 failed 後，使用者可『僅重試保存』」改為還要存檔和失敗那次的底對得上；不同時改給「改用存檔內容」。
- ADR-0302 第 3 點與「後果」：「接不上照舊整棵寫回」與「心跳寫入後按僅重試保存仍會蓋掉」不再成立：接不上又有別人的內容時不准重試。
- ADR-0300 第 10 點：存檔失敗時仍不顯示「有新內容」提示，改由存檔失敗的畫面提供「改用存檔內容」。

## 後果

- 心跳、別的裝置、工具寫進的內容不會再被重試蓋掉。
- 一輪回覆中工具改了設定（例如中途啟用技能，ADR-0231 第 2 點），而回覆收尾存檔又失敗時，只能改用存檔內容：回覆文字還在，但這一輪的工具步驟、思考過程和失敗標示的顯示會不見。反過來說，原本按重試會把工具剛啟用的技能默默撤銷。想保住完整顯示，可以之後再做「只把自己那則回覆換成完整版、接在存檔上」。
- 存檔被別人改過時，這一頁沒存進去的回覆不會自動接到心跳後面：那則訊息是在沒看到心跳時寫的，硬接上去會改變前後文；三方合併另做。
- 同意匯入覆蓋之後到真正寫入之間（中間可能停在選靈魂的視窗），那段對話如果被心跳寫入，也會一起被覆蓋。這在使用者同意的範圍內；看不到的對話後端照樣拒絕。
- 回覆收尾那一種比版本號，後端重啟後只能改用存檔內容。

## 驗證

- `SessionListProvider.retryGuard.test.tsx`：心跳寫過不准重試也不送出、改用存檔內容後看得到心跳內容且下一則用存檔版本送出；回應遺失加後端重啟仍可重試；工具改設定不准重試；改用存檔內容會重讀、存檔被刪不換內容；回覆收尾兩種版本；匯入同意與不同意、讀完到送出之間有人寫、回應遺失後重試。
- 同檔另有：這一頁新建、欄位不齊的對話仍可重試；存檔前讀存檔失敗仍可重試；改用存檔內容換不成時有提示。
- `session_persistence.test.ts` 的 `sameStoredBase`（只比重試會送出的欄位）；`SessionPersistenceNotice.test.tsx`（換了對話後才按確認不生效）；`useSessionEvents.test.tsx`（只有畫面上已有的編號帶覆蓋同意）；`ChatProvider.backgroundStream.test.tsx`（重新載入時模式跟著重抓的結果）。
- `SessionListProvider.syncSession.test.tsx` 原本把「蓋掉別人」當正確的三條改成存檔沒人動過的情境，或改走匯入同意覆蓋。
- 實際驗證 `session-attention.spec.ts`：心跳寫入 → 送訊息存檔失敗 → 重新核對 → 沒有重試 → 改用存檔內容 → 訊息還在輸入框 → 再送，存檔裡心跳的回覆和新的回覆都在。
