# ADR-0302：聊天側剪裁先等畫面的收尾保存

- 狀態：✅ 已實作。一頁計畫由維護者核准（路線圖 3c，2026-11-06），計畫經兩輪審查。
- 日期：2026-11-06
- 決策者：維護者
- 相關：ADR-0231（對話保存的版本與恢復，本 ADR 修訂它的第 6、8、10 點）、ADR-0092（滑動視窗剪裁）、ADR-0301（家標記不算進版本）、ADR-0276（換綁靈魂）、ADR-0295（實際驗證）。
- 影響範圍：`ToukaProxy/src/services/chat_trim_wait.py`・`src/services/dispatcher.py`・`src/services/sliding_window_service.py`・`src/services/stream_buffer_service.py`・`src/routers/ui_sessions.py`＋`ToukaChat/src/lib/trim_graft.ts`・`src/lib/providers/SessionListProvider.tsx`＋`tests/fixtures/sliding_window_trim.json`。

## 背景

網頁版一輪回覆結束時，後端先把文字版存起來，送出終態；畫面收到終態，再把富版（工具步驟、思考等）整棵存一次。開了滑動視窗時，後端在文字版存好後就在背景開始剪裁：讀存檔、歸檔、寫摘要（一次模型呼叫，要幾秒）、帶讀到的版本存回。

兩邊搶同一個版本。畫面的收尾保存通常先到，剪裁存回時版本對不上就作罷，摘要的模型呼叫白花，下一則再重來一次。畫面慢的時候反過來：剪裁存好，畫面那次被擋，要按「重新核對」「僅重試保存」；「僅重試保存」會把整棵舊樹寫回去，等於撤銷剪裁。實際驗證「剪裁（聊天）」那條只能先恢復再送（ADR-0295）。

## 決定

1. **後端：剪裁先等畫面的收尾保存**（`chat_trim_wait`）。
   - `_pump_ui_stream` 文字版存好後、送出終態前，同步登記一個等待者（中間不經 await），記下文字版的版本、這一輪的助理節點與送出的人。版本含讀的人的身分，所以之後用送出的人重讀才比得起來。
   - 保存端點（`POST /v1/ui/sessions/{id}`）存好時叫醒它，不反覆讀檔。開始等之前先重讀一次：存檔已經離開文字版（畫面已經存了），就不等。
   - 上限是 `CLOSING_SAVE_WAIT_SECONDS`（10 秒；收尾保存通常在終態後一秒內就到）。逾時就照舊，以當下的存檔剪（頁面關掉、網路斷掉時）。
   - 同一段對話只留一個等待者：新的一輪登記時，舊的直接結束、不剪。
   - 等待在每對話鎖外，讀與存回在鎖內。觸發點、`spawn_logged` 與鎖都不變（禁令 28、57 的意思不變）。非網頁的 `_pump_stream_to_buffer` 沒有畫面補存，不等。
2. **放棄條件**（`check_and_trim(..., abandon)`）：讀到存檔後、寫摘要前（重讀一次，版本變了也放棄，省下模型呼叫）、存回前各查一次，任一成立就不剪：
   - 這段對話有心跳在跑：心跳結束時自己會剪，也避開心跳存檔造成的變動。
   - 有正在跑的回覆，或有還沒開始串流的請求（`stream_buffer_service.is_busy`，不分是誰送的）。
   - 存檔的最後一則已經不是這一輪的回覆：使用者已經存下一則。

   心跳那個觸發點不帶放棄條件，照舊。
3. **畫面：被擋時接在剪過的存檔上。** 存檔因為版本舊被擋（`failed`）時讀一次存檔，用 `graftOntoTrim` 判斷是不是剪裁造成的。是的話，以剪過的存檔為底接上這一頁的改動，存一次，不跳提示。只接一次；接完再被擋，照舊提示。一般保存、回覆收尾、「僅重試保存」用同一套接法；接不上時「僅重試保存」照舊整棵寫回去，等於撤銷剪裁。
   - **算剪裁造成的**，看形狀，要全部符合：
     - 存檔只有一條主幹，第一則沒有 parentId。
     - 主幹是本機確認過的主幹的後段：除了上下連結，節點內容都相同。
     - 其他欄位（標題、靈魂、模式等）沒變，而且至少剪掉一則。
     - 逾時那條路剪的是文字版：存檔最後多一則「本機確認過的還沒有、本機有」的助理回覆，也算。

     只看形狀，所以另一個分頁的手動切分、心跳那個觸發點的剪裁，形狀一樣時也當成剪裁接上。
   - **接法：**
     - 結果只有兩種節點：存檔留下、這一頁也還留著的；這一頁新增、祖先在結果裡接得上的。這一頁刪掉或切分掉的不寫回去。
     - 內容與上層以這一頁為準（上一則不在結果裡，這則就成了第一則），下層只留結果裡有的。
     - 下列情況照舊提示：本機改過的節點已被剪掉或丟掉（含在底下接新的一則）；新節點接在被剪的範圍或主幹外的分支上；目前所在的那一則不在結果裡；樹讀不懂（讀的時候出錯）。
     - 剪掉的前段、主幹外的分支與摘要，一律以存檔為準。
   - **兩邊用同一份樹的範例：** 判斷用的樹形狀由後端真的剪裁函式驗過（`tests/fixtures/sliding_window_trim.json`；pytest 確認它就是 `_rebuild_tree` 的輸出，vitest 讀它），兩邊不會各寫各的、漸漸對不上。

## 取捨與影響

- 剪裁生效後，開著的對話上方的舊訊息，在下一次保存後會從畫面消失（Owner 2026-11-06 同意）。靈魂靠摘要記得前面的內容。
- 剪裁本來就會丟掉保留範圍裡主幹外的分支，而且不歸檔（既有行為）。以前畫面會跳提示，現在默默接受。
- 接法偏保守：剪裁之後在這一頁刪掉被剪範圍裡的一條旁支，也算改過被剪掉的那則，照舊提示；這時按「僅重試保存」會撤銷剪裁。很少見，不會丟內容。
- 寫摘要的那幾秒內剛好送出下一則時，那次摘要還是白花（存回前查到就放棄）。
- 家對話的每一輪網頁回覆，多一次讀檔（開始等之前）；畫面保存被擋時，也多一次讀檔。
- 心跳寫進開著的對話之後按「僅重試保存」，仍會蓋掉心跳寫入的內容。這是既有問題，不是剪裁造成的，接法不處理（見 `docs/handover/chat.md`）。
- ADR-0295 曾寫「舊對話庫每次多一份」，並不成立：歸檔按訊息編號只新增，剪裁輸掉兩次，訊息數也不變（`test_trims_that_lose_twice_do_not_duplicate_the_archive`）。log 的 `archived %d` 是「確認在庫」的則數，每次都一樣。
